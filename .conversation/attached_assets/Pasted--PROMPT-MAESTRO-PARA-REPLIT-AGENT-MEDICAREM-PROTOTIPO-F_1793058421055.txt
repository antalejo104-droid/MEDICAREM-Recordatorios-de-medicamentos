# PROMPT MAESTRO PARA REPLIT AGENT: MEDICAREM — PROTOTIPO FUNCIONAL CON OBJETIVO TRL 5

## 1. Rol y misión

Actúa como un equipo multidisciplinario compuesto por un arquitecto de software, desarrollador full-stack, desarrollador móvil, especialista en bases de datos, diseñador UX/UI, ingeniero de pruebas y especialista en seguridad de aplicaciones.

Debes diseñar, programar, integrar, probar y documentar **MEDICAREM**, un sistema digital de recordatorio y monitoreo de medicamentos para adultos mayores, con el objetivo de desarrollar un prototipo integrado que pueda ser evaluado para alcanzar, como mínimo, los criterios de madurez tecnológica TRL 5.

No construyas solamente una landing page, una maqueta visual ni un prototipo con botones sin funcionalidad. Implementa un sistema de extremo a extremo con persistencia real de datos, autenticación, permisos, recordatorios, historial, sincronización y pruebas automatizadas.

Trabaja directamente en el proyecto de Replit. Crea los archivos, instala las dependencias necesarias, ejecuta la aplicación, resuelve errores y verifica los flujos funcionales. No te limites a describir lo que habría que programar.

Si una funcionalidad depende de permisos del dispositivo, servicios externos o configuración adicional, implementa la mejor alternativa funcional disponible, documenta los requisitos y no simules que la función funciona cuando no sea así.

## 2. Contexto académico y propósito del proyecto

**Nombre:** MEDICAREM.

**Título:** Sistema digital de recordatorio y monitoreo de medicamentos para adultos mayores.

**Tipo de proyecto:** Proyecto Aplicado de Ingeniería de Sistemas.

**Población objetivo:** Adultos mayores de 60 años, familiares y cuidadores autorizados de Pasto, Nariño, Colombia.

**Problema que se busca abordar:** La organización de medicamentos, dosis y horarios puede resultar compleja para algunos adultos mayores. La información sobre los eventos de medicación también puede estar dispersa, lo que dificulta su consulta y el acompañamiento por parte de familiares o cuidadores.

**Objetivo general:** Desarrollar un prototipo digital accesible de recordatorio y monitoreo de medicamentos para adultos mayores de Pasto, mediante una aplicación móvil y un panel web que faciliten la organización de horarios, el registro de tomas y el seguimiento por familiares o cuidadores autorizados.

El sistema debe apoyar la organización personal de los medicamentos. No debe reemplazar a médicos, farmacéuticos ni otros profesionales de la salud.

## 3. Objetivo de madurez tecnológica: TRL 5

Desarrolla MEDICAREM para que sus componentes principales estén integrados y puedan probarse en un entorno relevante simulado que represente las condiciones previstas de uso.

Para respaldar la evaluación de TRL 5, el sistema debe contar con:

1. Aplicación móvil funcional y panel web integrados.
2. Base de datos persistente y modelo de datos coherente.
3. Comunicación entre los componentes mediante una API segura.
4. Flujos completos de registro de medicamentos, programación, recordatorios, respuestas e historial.
5. Gestión de cuentas, autenticación y permisos de cuidadores.
6. Sincronización de datos y manejo de interrupciones de conectividad.
7. Interfaz accesible y evaluable con adultos mayores.
8. Pruebas funcionales, de integración, seguridad básica, sincronización y usabilidad.
9. Entorno de pruebas representativo, con datos ficticios y escenarios realistas.
10. Evidencias documentadas de los resultados, defectos encontrados, correcciones y limitaciones.

**No declares automáticamente que MEDICAREM alcanzó TRL 5 por estar programado o desplegado.** Debes entregar una evaluación de criterios con resultados verificables. Si faltan pruebas en el entorno relevante o evidencia suficiente, indica que el sistema está preparado para esa evaluación, pero que el nivel no ha sido demostrado todavía.

## 4. Arquitectura tecnológica

Selecciona una arquitectura moderna, mantenible y compatible con las herramientas disponibles en Replit.

Preferencias tecnológicas:

- Aplicación móvil: React Native con Expo y TypeScript, si el entorno de desarrollo permite construir y probar correctamente el proyecto móvil.
- Panel web: React con TypeScript y un diseño adaptable.
- Backend: Node.js con TypeScript y una API REST.
- Base de datos: PostgreSQL.
- ORM y migraciones: Prisma o una alternativa equivalente compatible con PostgreSQL.
- Autenticación: sesiones seguras o tokens de acceso implementados correctamente.
- Validación: Zod o una alternativa equivalente.
- Pruebas: Vitest o Jest y pruebas de API con Supertest, Playwright u opciones equivalentes.
- Control de versiones: estructura organizada y documentación clara.

Puedes modificar el stack si existe una limitación técnica real, pero debes justificar el cambio. No sustituyas una aplicación móvil por una página estática y no afirmes que una PWA ofrece notificaciones nativas idénticas en todas las plataformas.

Si no puedes construir y ejecutar directamente la aplicación Android en Replit, desarrolla el proyecto móvil con una estructura compatible con Expo, implementa el panel web y el backend, y documenta exactamente cómo compilar y probar el APK en un entorno compatible. Prioriza mantener una arquitectura integrada y funcional.

Estructura lógica:

Aplicación móvil Android ↔ API y servicio de sincronización ↔ Base de datos PostgreSQL ↔ Panel web para cuidadores autorizados.

La aplicación móvil debe poder realizar las funciones locales de recordatorio cuando no haya Internet. Las consultas remotas y el panel web dependerán de la conexión y de la sincronización.

## 5. Tipos de usuarios y permisos

Implementa al menos los siguientes roles:

### A. Adulto mayor o usuario principal

Puede:
- Crear y administrar su perfil.
- Registrar medicamentos y horarios.
- Consultar sus recordatorios.
- Confirmar una toma mediante autorreporte.
- Declarar una omisión.
- Consultar su historial.
- Autorizar y revocar el acceso de un cuidador.
- Consultar el estado de sincronización.

### B. Familiar o cuidador autorizado

Puede:
- Crear su cuenta.
- Solicitar o aceptar una vinculación autorizada con un usuario.
- Consultar únicamente los datos permitidos por la autorización.
- Consultar los eventos de medicación disponibles.
- Recibir avisos sobre omisiones declaradas.
- Consultar el historial y la fecha de última sincronización.

No puede:
- Acceder a usuarios que no lo hayan autorizado.
- Modificar medicamentos del adulto mayor sin un permiso explícito y definido.
- Consultar información privada fuera del alcance de su autorización.

### C. Administrador técnico

Implementa un mecanismo administrativo seguro para la gestión técnica del prototipo. No permitas acceso irrestricto a datos personales por defecto.

La interfaz de administración no debe mostrar datos médicos personales innecesarios.

## 6. Funcionalidades obligatorias

### 6.1. Registro y autenticación

Implementa:
- Registro e inicio de sesión.
- Cierre de sesión.
- Recuperación de acceso mediante un mecanismo seguro, cuando esté disponible.
- Validación de campos.
- Contraseñas almacenadas con hash seguro.
- Control de acceso por roles.
- Protección de rutas privadas.
- Mensajes de error comprensibles.
- Prevención de acceso a recursos de otros usuarios mediante cambios manuales de identificadores.

No almacenes contraseñas en texto plano ni incluyas secretos directamente en el código.

### 6.2. Perfil del usuario

Permite registrar los datos mínimos necesarios para el funcionamiento del sistema.

Incluye:
- Nombre visible o alias.
- Correo electrónico para la cuenta.
- Preferencias de accesibilidad.
- Zona horaria.
- Preferencias de notificaciones.
- Estado de la cuenta.

Solicita únicamente los datos personales necesarios. No incluyas números de identificación, historia clínica u otros datos sensibles que no sean necesarios para el prototipo.

### 6.3. Gestión de medicamentos

Implementa un CRUD completo para:
- Nombre del medicamento.
- Presentación o descripción.
- Dosis prescrita introducida por el usuario según su indicación médica.
- Horarios programados.
- Fecha de inicio.
- Fecha de finalización opcional.
- Notas opcionales.
- Estado activo o inactivo.

Permite crear, consultar, editar, desactivar y visualizar medicamentos.

Las modificaciones de la configuración deben quedar registradas de forma coherente. No cambies automáticamente la dosis ni recomiendes tratamientos.

### 6.4. Programación y recordatorios

Permite:
- Crear uno o varios horarios diarios.
- Configurar días de la semana.
- Configurar la fecha de inicio y finalización cuando corresponda.
- Mostrar el próximo evento programado.
- Generar notificaciones en el dispositivo compatible.
- Gestionar permisos de notificación.
- Mostrar estados claros para cada evento.

Implementa notificaciones locales en el dispositivo móvil cuando la plataforma lo permita. Si existen restricciones del sistema operativo, explícalas y ofrece una alternativa funcional dentro de la aplicación.

Los horarios deben manejar correctamente la zona horaria configurada. Evita duplicar eventos al sincronizar o reiniciar la aplicación.

### 6.5. Registro de eventos

Cada evento programado debe tener un identificador único y un estado claramente definido.

Estados mínimos:

- `PENDING`: pendiente.
- `CONFIRMED`: toma confirmada mediante autorreporte.
- `DECLARED_OMISSION`: omisión declarada por el usuario.
- `UNCONFIRMED`: no existe confirmación del usuario.

No marques automáticamente una toma como omitida solo porque el usuario no respondió a una notificación.

Cuando el usuario confirme una toma, registra la hora del evento y la hora del autorreporte.

Cuando declare una omisión, registra la fecha, el evento correspondiente y la hora del reporte.

Evita confirmaciones duplicadas y conserva la trazabilidad de las modificaciones relevantes.

### 6.6. Panel web para cuidadores

Desarrolla un panel web adaptable que incluya:
- Inicio de sesión.
- Lista de usuarios vinculados y autorizados.
- Resumen de eventos recientes.
- Historial de tomas confirmadas.
- Historial de omisiones declaradas.
- Eventos pendientes o no confirmados.
- Fecha y hora de última sincronización.
- Avisos relacionados con omisiones declaradas.
- Gestión de autorizaciones.

No muestres eventos como confirmados u omitidos sin que exista un registro que respalde ese estado.

Los cuidadores solo deben ver la información autorizada por cada usuario.

### 6.7. Sincronización y funcionamiento sin conexión

Implementa:
- Persistencia local para los horarios necesarios para los recordatorios.
- Cola local de eventos pendientes de sincronización.
- Reintentos de sincronización.
- Identificadores únicos e idempotencia para prevenir duplicados.
- Indicador de conexión.
- Fecha y hora de última sincronización exitosa.
- Manejo de errores y recuperación después de interrupciones.

Cuando no exista conexión, conserva los eventos localmente y sincronízalos cuando se recupere la conexión.

Si existen conflictos de sincronización, aplica reglas explícitas y documentadas. No sobrescribas silenciosamente datos importantes.

En el panel web, muestra claramente cuándo los datos son antiguos y cuál fue la última sincronización. No presentes la información como tiempo real si no está actualizada.

### 6.8. Historial y reportes

Implementa una vista histórica con filtros por:
- Fecha.
- Medicamento.
- Estado del evento.

Incluye un resumen descriptivo de:
- Eventos programados.
- Confirmaciones registradas.
- Omisiones declaradas.
- Eventos sin confirmar.

Diferencia siempre los eventos no confirmados de las omisiones declaradas.

Puedes incluir gráficas sencillas, pero no generes diagnósticos ni afirmaciones clínicas a partir de los datos registrados.

## 7. Accesibilidad y experiencia de usuario

La aplicación debe estar diseñada para personas mayores de 60 años.

Incluye:
- Textos legibles y escalables.
- Contraste adecuado.
- Botones grandes y claramente etiquetados.
- Iconos acompañados de texto cuando sea necesario.
- Navegación sencilla.
- Formularios breves.
- Mensajes en español claro.
- Confirmaciones antes de acciones importantes.
- Errores comprensibles y recuperables.
- Compatibilidad con las opciones de accesibilidad disponibles en la plataforma.
- Alternativas para no depender exclusivamente del color.
- Evitar animaciones innecesarias.
- No depender únicamente de gestos complejos.

Para el panel web, utiliza WCAG 2.2 nivel AA como referencia de evaluación, sin afirmar conformidad total hasta completar las comprobaciones correspondientes.

Idioma inicial: español de Colombia.

Formato de fechas: día/mes/año en la interfaz.

Utiliza una apariencia profesional, tranquila, clara y coherente con una herramienta de apoyo a la salud. No satures la interfaz con gráficos ni información innecesaria.

## 8. Seguridad y protección de datos

MEDICAREM manejará información personal relacionada con medicamentos. Implementa protección desde el diseño.

Requisitos:
- HTTPS en entornos desplegados.
- Validación de entradas en el servidor.
- Consultas parametrizadas o uso seguro del ORM.
- Control de acceso en cada operación sensible.
- Contraseñas con hash seguro.
- Gestión segura de sesiones y tokens.
- Variables sensibles mediante Secrets o variables de entorno.
- Restricciones de acceso entre usuarios.
- Registro de eventos relevantes de auditoría.
- Protección contra exposición accidental de información en logs.
- Autorización explícita para compartir información con cuidadores.
- Posibilidad de revocar una autorización.
- Política de retención y eliminación de datos del prototipo.
- Copias de seguridad cuando el entorno lo permita.
- Documentación de limitaciones y riesgos conocidos.

Separa el consentimiento para participar en pruebas de la autorización para tratar datos personales y compartir información con cuidadores.

No uses información personal real durante las pruebas iniciales. Emplea datos ficticios y cuentas de prueba.

No presentes el prototipo como certificado, auditado legalmente o apto para producción si no se ha realizado la evaluación correspondiente.

## 9. Límites médicos y de seguridad

MEDICAREM es una herramienta de apoyo a la organización y al registro de eventos de medicación.

No debe:
- Diagnosticar enfermedades.
- Prescribir medicamentos.
- Recomendar dosis.
- Modificar tratamientos.
- Detectar interacciones farmacológicas como si fuera un sistema clínico validado.
- Decidir qué debe hacer el usuario después de declarar una omisión.
- Afirmar que se ha ingerido un medicamento basándose únicamente en una confirmación digital.
- Interpretar automáticamente un evento no confirmado como una omisión.
- Sustituir la atención de profesionales de la salud.
- Presentar sus reportes como evidencia clínica validada.

Utiliza textos informativos claros que indiquen que el usuario debe seguir las indicaciones de su profesional de salud.
